---
title: Storage layout
description: Where dither's bookkeeping and your markdown library live, and what's safe to back up.
---

dither separates two roots on disk:

- **dither home** — dither's own bookkeeping (config, plugins, grants, runs, locks, logs, daemon state, qmd index). By default `~/.dither/`. Override with `DITHER_HOME`.
- **library** — the markdown content dither indexes and writes into. Configurable per-install. Defaults to `<dither-home>/library/` for fresh users; `dither init --library <path>` points it anywhere you like.

```bash
export DITHER_HOME=/path/to/dither-home   # optional, rarely needed
```

The split keeps "your stuff" (markdown) cleanly separated from "dither's bookkeeping" (everything else). You can back up the library independently, hand its path to an agent without exposing dither's internals, or point it at a folder you already curate.

## dither home

| Path                                            | Purpose                                                                    | Written by                         |
| ----------------------------------------------- | -------------------------------------------------------------------------- | ---------------------------------- |
| `<dither-home>/config.json`                     | The library path and schema version. Written by `dither init`.             | `dither init`                      |
| `<dither-home>/qmd-index.sqlite`                | The qmd search index over the library.                                     | `dither index update`, plugin runs |
| `<dither-home>/env.json`                        | The dither-managed global env store. Plain JSON, names → values.           | `dither env set/unset`             |
| `<dither-home>/plugins/<name>/`                 | Installed plugin source — copied verbatim from the install path.           | `dither plugin install`            |
| `<dither-home>/plugins/<name>/state/state.json` | Plugin's persistent state (e.g. last-synced cursor).                       | The plugin itself, at run time     |
| `<dither-home>/grants/<name>.json`              | dither-owned record of the plugin's manifest snapshot and resolved grants. | `dither plugin install`            |
| `<dither-home>/runs/<run-id>/`                  | Per-run scratch dir. The plugin writes its `*.md` output here.             | `dither plugin run` (auto-cleaned) |
| `<dither-home>/logs/<name>-<ts>.log`            | Captured stdout/stderr of `dither plugin run --detach`.                    | `dither plugin run --detach`       |
| `<dither-home>/locks/`                          | Per-plugin lock files used to serialise concurrent runs.                   | `dither plugin run`, daemon        |
| `<dither-home>/bin/deno-<version>`              | dither-managed Deno binary used to spawn plugins. SHA-verified at install. | `dither plugin install` / `run` (lazy bootstrap) |

`runs/<run-id>/` is ephemeral. After a successful promote the host removes it. Don't put anything you care about in there.

## The library

The library is one directory containing your markdown. Each top-level subdirectory is a [collection](/docs/concepts/collections). Plugins promote files into collection subdirs after their grants are checked.

```
<library>/
  notes/        ← top-level subdir = collection "notes"
    auth.md
  messages/
    tom/
      2026-05-...md
  imported/
    fixture-1.md
```

Where the library lives is your choice at `dither init`:

- **No flag** → `<dither-home>/library/`. Self-contained, easy default.
- **`--library <path>`** → adopt or create at that path. Recommended for users who want their markdown in a familiar location, e.g. `~/Documents/dither/`.

The path is canonicalised (via `realpath`) at init time, so symlinks don't silently widen the configured scope later.

## Initialising

`dither init` is the required first step. Until it has run, library-needing commands (`search`, `get`, `index update`, `plugin install`, `plugin run`, `daemon start`) refuse with:

```
error: dither is not initialized. Run `dither init` to set up your library.
```

See [`dither init`](/docs/cli/init) for flags and reconfiguration.

## The grants file

`<dither-home>/grants/<name>.json` is dither's record of what a specific plugin is allowed to do:

```json
{
  "name": "my-plugin",
  "version": "0.1.0",
  "installedAt": "2026-05-01T12:00:00Z",
  "manifest": {
    /* the plugin's declared shape, frozen at install */
  },
  "env": { "MAX_RETRIES": "5" },
  "envRefs": ["OPENAI_API_KEY"],
  "files": { "SOURCE": "/abs/path/to/file" },
  "net": ["api.openai.com"],
  "collections": ["notes"]
}
```

The five grant fields (`env`, `envRefs`, `files`, `net`, `collections`) are described in detail in [Security](/docs/concepts/security). `collections` are glob patterns over collection paths within the library; the example above grants only the literal `notes` collection. A grant like `["messages/**"]` authorises all descendants of `messages`. `manifest` is captured at install time so reinstalls and runs use a stable declaration.

## The global env store

`<dither-home>/env.json` is the dither-managed env namespace. It has nothing to do with shell env vars — dither owns its own. Plugins granted `--allow-env KEY` read these values (looked up by name at every run). See [`dither env`](/docs/cli/env).

```json
{ "OPENAI_API_KEY": "sk-...", "ANTHROPIC_API_KEY": "..." }
```

## What the architecture reserves but isn't yet written

A few paths are mentioned in the architecture sketch but aren't produced by the current CLI. They will appear in later phases without breaking layout:

- `<library>/attachments/<uuid>/<filename>` — blob storage for entry attachments. Not yet wired up; `attachments[]` frontmatter parses but isn't materialised.
- `<dither-home>/dither.sock`, `<dither-home>/dither.sqlite` — daemon IPC and run-history database (a per-run journal exists today; an aggregated SQLite store is parked).
- `<dither-home>/keys/dither.sqlite` — API key store for agent access (MCP). No agent surface yet.
- `<dither-home>/collections.json` — collection id-to-name registry. Today, collections are keyed by folder name.

If you see these paths today, they're left over from another tool or a future build.

## The qmd index

`<dither-home>/qmd-index.sqlite` is the local SQLite database qmd writes when you run `dither index update` or after a plugin promote. It's a derived artifact: drop it, run `dither index update`, and it rebuilds from the library.

The index always lives in dither home, regardless of where the library is. If you point dither at a folder that's also indexed by qmd-CLI elsewhere, the two indices are independent — they don't share state. (See `notes/qmd-index-reuse.md` in the repo for the design parked for later.)

You should not edit this file by hand. Treat it the way you'd treat a build cache.

## What to back up

The library plus `env.json`.

The library is your corpus. `env.json` is the only place your global env values exist on disk — losing it means re-supplying every API key.

Everything else is regenerable:

- `qmd-index.sqlite` — rebuilds from the library via `dither index update`.
- `plugins/<name>/` — reinstall with `dither plugin install`.
- `plugins/<name>/state/` — plugin will resync from scratch (this can mean re-fetching from APIs; not always cheap, but never lossy for _your_ data).
- `grants/<name>.json` — recreated by reinstalling the plugin and re-supplying grant flags.
- `config.json` — recreated by `dither init` (you'll need to re-pass `--library <path>` if you used a non-default location).
- `runs/<run-id>/`, `logs/` — already ephemeral.

A `tar` of the library directory plus a copy of `<dither-home>/env.json` is a complete backup of your dither user data. Pair it with the plugin source (or your install commands) and you can rebuild the rest in minutes.
