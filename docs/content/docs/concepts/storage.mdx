---
title: Storage layout
description: What lives under ~/.dither/, what's safe to back up, and what's regenerable.
---

Everything dither keeps on disk lives under a single directory. By default that's `~/.dither/`. Override with the `DITHER_HOME` env var:

```bash
export DITHER_HOME=/path/to/dither-home
```

When `DITHER_HOME` is unset, dither resolves to `~/.dither` on every platform.

## What's there today

| Path | Purpose | Written by |
| --- | --- | --- |
| `~/.dither/entries/<collection>/**/*.md` | Your canonical markdown. One folder per collection. | You + plugins (via promote) |
| `~/.dither/qmd-index.sqlite` | The qmd search index over `entries/`. | `dither index update`, plugin runs |
| `~/.dither/plugins/<name>/` | Installed plugin source — copied verbatim from the install path. | `dither plugin install` |
| `~/.dither/plugins/<name>/state/state.json` | Plugin's persistent state (e.g. last-synced cursor). | The plugin itself, at run time |
| `~/.dither/grants/<name>.json` | dither-owned record of the plugin's manifest, resolved input values, and file paths. | `dither plugin install` |
| `~/.dither/runs/<run-id>/` | Per-run scratch dir. The plugin writes its `*.md` output here. | `dither plugin run` (auto-cleaned) |

Two paths to know about:

- `entries/<collection>/` is the only directory whose contents are *yours* in the strong sense. Everything else is bookkeeping.
- `runs/<run-id>/` is ephemeral. After a successful promote, the host removes it. Don't put anything you care about in there.

## What the architecture reserves but v0 doesn't write

A few paths are mentioned in the architecture sketch but aren't produced by the v0 CLI. They will appear in later phases without breaking layout:

- `~/.dither/attachments/<uuid>/<filename>` — blob storage for entry attachments. Not yet wired up; `attachments[]` frontmatter parses but isn't materialised.
- `~/.dither/dither.sock`, `~/.dither/dither.pid`, `~/.dither/dither.sqlite` — daemon IPC, PID, and run-history database. There's no daemon in v0.
- `~/.dither/keys/dither.sqlite` — API key store for agent access (MCP). No agent surface in v0.
- `~/.dither/collections.json` — collection id-to-name registry. v0 keys collections by folder name only.

If you see these paths today, they're left over from another tool or a future build.

## The qmd index

`~/.dither/qmd-index.sqlite` is the local SQLite database that qmd writes when you run `dither index update` or after a plugin promote. It's a derived artifact: drop it, run `dither index update`, and it rebuilds from `entries/`.

You should not edit this file by hand. Treat it the way you'd treat a build cache.

## What to back up

Just `entries/`.

Everything else is regenerable:

- `qmd-index.sqlite` — rebuilds from `entries/` via `dither index update`.
- `plugins/<name>/` — reinstall with `dither plugin install`.
- `plugins/<name>/state/` — plugin will resync from scratch (this can mean re-fetching from APIs; not always cheap, but never lossy for *your* data).
- `grants/<name>.json` — recreated by reinstalling the plugin and re-supplying inputs.
- `runs/<run-id>/` — already ephemeral.

A `tar` of `~/.dither/entries/` is a complete backup of your dither corpus. Pair it with a copy of any plugin install commands you used (or just keep the plugin source somewhere) and you can rebuild the rest in minutes.
